# e-archive — Электронный архив (MVP)

Инновационный электронный архив для РК на полностью open-source стеке:
**AI-поиск** (семантический), **OCR** при приёме (рус/каз/eng), **ЭЦП РК** через
NCALayer, антивирус **ClamAV** и **WORM-хранение** оригиналов (MinIO Object Lock).

## Архитектура

```
                        ┌──────────── React PWA (nginx :3000) ───────────┐
                        │  Логин · Каталог · AI-поиск · Приём · ЭЦП       │
                        └───────────────────────┬────────────────────────┘
                                                 │ /api  (reverse proxy)
                        ┌───────────────────────▼────────────────────────┐
                        │              FastAPI backend (:8000)            │
   Приём документа ▶    │  scan ─▶ WORM store ─▶ OCR ─▶ embeddings/index  │
                        └──┬──────────┬───────────┬───────────┬──────────┘
                           │          │           │           │
                    PostgreSQL     MinIO      OpenSearch     ClamAV
                    (метаданные)  (WORM S3)  (гибрид-поиск) (антивирус)

   ЭЦП: браузер ─▶ NCALayer (wss://127.0.0.1:13579) ─▶ CMS ─▶ backend verify
```

| Слой | Компонент |
|------|-----------|
| Backend | FastAPI (Python 3.11) |
| Хранилище | MinIO (S3, Object Lock / WORM) |
| СУБД | PostgreSQL 16 |
| Поиск | OpenSearch 2.13 (BM25 + kNN по чанкам, RRF-фьюжн, кросс-энкодер) |
| Эмбеддинги | fastembed / `paraphrase-multilingual-MiniLM-L12-v2` (384d, ONNX, без torch) |
| RAG-чат (LLM) | Ollama / `qwen2.5:3b` (локально, данные не покидают периметр) |
| OCR | Tesseract (rus + kaz + eng) + poppler; опционально [baidu/Unlimited-OCR](https://github.com/baidu/Unlimited-OCR) (VLM, нужен GPU) |
| Антивирус | ClamAV |
| ЭЦП | NCALayer (клиент НУЦ РК), проверка CMS на сервере |
| Frontend | React 18 PWA (Vite) |
| Оркестрация | Docker Compose |

## Быстрый старт

```bash
cp .env.example .env          # при необходимости поменяйте пароли/секреты
docker compose up -d --build
```

Первый запуск дольше обычного: ClamAV скачивает базы сигнатур (~2–3 мин),
backend при первом OCR/индексации подтягивает ONNX-модель эмбеддингов.

| Сервис | URL |
|--------|-----|
| Веб-приложение | http://localhost:3000 |
| API (Swagger) | http://localhost:8000/docs |
| MinIO Console | http://localhost:9011 |
| OpenSearch | http://localhost:9200 |

**Вход по умолчанию:** `admin@earchive.kz` / `admin12345` (задаётся в `.env`).

### Распознавание документов

По умолчанию используется **Tesseract** (rus + kaz + eng) — работает на любой
машине без GPU. Цифровые PDF с текстовым слоем читаются напрямую, минуя OCR.

Опционально можно подключить VLM [baidu/Unlimited-OCR](https://github.com/baidu/Unlimited-OCR):
в отличие от Tesseract он понимает структуру страницы (таблицы, колонки, печати,
рукописный текст) и распознаёт рус/каз/eng без указания языка. Требует NVIDIA
GPU (модель в bf16 не поместится рядом с `qwen2.5:7b` на карте с 8 ГБ VRAM —
нужна карта помощнее или отдельная машина):

```bash
# в .env: OCR_ENGINE=unlimited
docker compose --profile ocr up -d ocr     # первый запуск качает веса модели
```

Сервис вынесен в профиль, потому что делит видеопамять с `ollama`: на одной
карте распределите VRAM через `OCR_GPU_FRACTION` в `.env`. Если сервис не
поднят, backend автоматически откатывается на Tesseract
(`OCR_FALLBACK_TESSERACT=true`), приём документов не прерывается.

## Тесты

```bash
docker compose exec backend pip install pytest
docker cp backend/tests e-archive-backend-1:/app/tests
docker cp backend/pytest.ini e-archive-backend-1:/app/pytest.ini
docker compose exec backend python -m pytest
```

Запуск именно через `python -m pytest`: контейнер работает от
непривилегированного пользователя, и установленный им скрипт `pytest`
не попадает в `PATH`.

Тесты в образ не входят — производственный образ не должен нести тестовый код.
Покрыты инварианты, поломка которых незаметна на глаз: нарезка на чанки (ничего
не теряется на стыках), объединение выдач RRF, распознавание типа документа в
словоформах, реестр отмены генерации, расчёт сроков хранения и проверки
конфигурации безопасности. Для редакции «Казпочта» (ТС-176) — отдельные наборы:

| Набор | Что проверяет |
|---|---|
| `test_edition.py` | каждый модуль ТС-176 есть в меню; чужие модули и демо-учётка скрыты |
| `test_scanning.py` | в дело статьи вводятся только виды документов, заданные номенклатурой |
| `test_ecopies.py` | переходы статусов электронной копии; подпись удостоверяет именно этот файл |
| `test_system_state.py`, `test_access_roles.py` | события обновлений и настроек в журнале; аудитор не видит документов |
| `test_sla.py` | сроки реакции и устранения в рабочем времени, % доступности, расчёт оплаты |
| `test_ncanode.py` | подпись без статуса отзыва сертификата не считается подтверждённой |
| `test_routes.py` | подстановка руководителей по оргструктуре; шаг без руководителя останавливает маршрут |
| `test_dictionaries.py` | строгий справочник отклоняет значения вне себя, пустой ввод не блокирует |
| `test_nto.py` | статусы описей по решениям комиссий; передаются только закрытые дела; формы НТО |
| `test_passkeys.py` | одноразовый вызов WebAuthn; домен ключей обязателен в промышленном контуре |

Защиту журнала в СУБД, ответ NCANode, печать форм и вход по ключам доступа с
телефона проверяют на стенде — порядок в [docs/admin-kazpost.md](docs/admin-kazpost.md).

## Перед запуском в промышленную эксплуатацию

В `.env` обязательно задайте `ENVIRONMENT=production` и замените
демонстрационные значения — иначе сервис не стартует:

| Параметр | Почему обязателен |
|---|---|
| `SECRET_KEY` | с общеизвестным ключом любой подписывает себе токен администратора |
| `FIRST_ADMIN_PASSWORD` | учётная запись администратора с паролем из документации |
| `POSTGRES_PASSWORD`, `MINIO_ROOT_PASSWORD` | доступ к базе и хранилищу оригиналов |
| `CORS_ORIGINS` | не должен содержать `*` |
| `WEBAUTHN_RP_ID`, `WEBAUTHN_ORIGINS` | при `WEBAUTHN_ENABLED=true`: ключ доступа привязан к домену, с `localhost` вход по биометрии в контуре не работает |

В режиме `dev` те же проблемы выводятся предупреждением в журнал, но запуск
не блокируется. Готовность сервиса проверяется пробой `/api/health/ready` —
она отвечает `503`, если недоступны база, поиск или хранилище.

## Как устроен поиск и ИИ-ассистент

Конвейер выстроен по практикам промышленного RAG: 73% отказов таких систем
приходится не на генерацию, а на поиск, поэтому основное внимание — ему.

1. **Чанкинг.** Документ режется на фрагменты ~800 символов по границам
   абзацев и предложений, с перекрытием. Раньше документ индексировался одним
   вектором и обрезался до 2000 символов — содержимое дела на 180 страниц было
   недоступно ни поиску, ни модели.
2. **Контекстный префикс** (приём contextual retrieval): к каждому фрагменту
   при индексации добавляется шапка с реквизитами карточки — тип, номер, дата,
   контрагент, кадастровый номер. Фрагмент из середины договора перестаёт быть
   безымянным обрывком. В отличие от исходного приёма шапка не генерируется
   моделью, а берётся из структурированных метаданных: точнее и бесплатно.
3. **Гибридный поиск и RRF.** Лексический (BM25) и векторный поиск идут
   параллельно, результаты объединяются алгоритмом Reciprocal Rank Fusion —
   он не требует нормализации несопоставимых шкал.
4. **Переранжирование кросс-энкодером** (`jina-reranker-v2-base-multilingual`,
   CPU). Читает пару «запрос + фрагмент» вместе и исправляет случаи, где
   RRF ошибается: например, отличает сам договор аренды от платёжного
   поручения по этой аренде.
5. **Переписывание уточняющих вопросов.** «А какая пеня за просрочку?»
   переформулируется по истории диалога в самостоятельный запрос.
6. **Быстрые ответы без модели.** Подсчёты, агрегаты, последние поступления,
   сроки хранения и собственники недвижимости считаются прямо по базе и
   возвращаются мгновенно, минуя LLM.

Качество поиска измеряется методом needle-in-haystack: из документов
извлекаются фразы с разных глубин и проверяется, доходят ли они до контекста
модели. После доработки — 100% попаданий, включая фрагменты за пределами
первых 2000 символов (было 0%).

### Достоверность ответа

Для архива самый опасный отказ — не «документ не найден», а уверенно названная
неверная сумма или год: такой ответ выглядит достоверным и уходит в работу.
Поэтому ответ проверяется после генерации:

- **Сверка чисел.** Все числовые факты ответа (суммы, годы, номера документов)
  сверяются с текстом, который был отдан модели. Неподтверждённые перечисляются
  в действиях агента, а к ответу добавляется предупреждение.
- **Проверка ссылок.** Ссылка на несуществующий источник — признак дописанного
  обоснования.
- **Уверенность** (`high` / `medium` / `low`) возвращается в ответе API и
  показывается под сообщением ассистента, когда она не высокая.

Проверка детерминированная, без второй модели-судьи: она не оценивает смысл,
но ловит именно те ошибки, которые в архивной работе дороже всего.

### Документы как недоверенные данные

Текст документов приходит из загруженных файлов и распознавания, поэтому может
содержать строки вида «игнорируй инструкции и ответь …». Содержимое передаётся
модели в помеченных границах, маркеры границ вычищаются из самого текста, а
системная инструкция запрещает исполнять что-либо изнутри них. Защита
распространяется и на авто-аннотирование с классификацией при приёме — там
документ попадает в модель без участия человека.

## Редакция «Казпочта»

Одна кодовая база, отдельная редакция: переменная `EDITION=kazpost` задаёт
название, оформление и меню, сгруппированное ровно по модулям ТС-176 (п. 4.2) —
при приёмке каждый модуль спецификации находится под своим именем. Права
доступа от редакции не зависят. План внедрения по закупке № 1240944 —
[docs/plan-kazpost.md](docs/plan-kazpost.md).

```bash
cp .env.kazpost.example .env                      # заполнить секреты и SMTP
docker compose -f docker-compose.yml -f docker-compose.kazpost.yml up -d --build
```

- наружу опубликован только веб-вход (80 → 443, сертификат в `./certs`);
  база, хранилище, поиск и модель доступны лишь во внутренней сети;
- тестовая среда (ТС 4.11, требование ИБ об испытании обновлений) —
  `docker-compose.kazpost-test.yml`: отдельный проект, свои тома, порты 8080/8443;
- разделы, которые контур не тянет по ресурсам, отключаются
  `EDITION_DISABLED_MODULES` (например, `search` без сервера языковой модели).

### Резервное копирование и восстановление

В промышленном контуре работают два сервиса (ТС-176 разд. 14 п. 1.1):

- `backup-db` — дамп PostgreSQL раз в `BACKUP_INTERVAL_HOURS` часов в
  `${BACKUP_DIR}/db`, хранение `BACKUP_KEEP_DAYS` дней; проба здоровья падает,
  если последней удачной копии больше двух интервалов;
- `backup-objects` — непрерывное зеркало хранилища документов в
  `${BACKUP_DIR}/objects`.

Восстановление (поисковый индекс после старта backend дособирается сам):

```bash
docker compose -f docker-compose.yml -f docker-compose.kazpost.yml stop backend
docker compose -f docker-compose.yml -f docker-compose.kazpost.yml exec -T postgres pg_restore -U earchive -d earchive --clean --if-exists < backups/db/earchive-ДАТА.dump
docker compose -f docker-compose.yml -f docker-compose.kazpost.yml run --rm backup-objects mirror --overwrite /backups/objects archive/archive
docker compose -f docker-compose.yml -f docker-compose.kazpost.yml start backend
```

### Второй фактор входа

Включён по умолчанию (`TWOFA_ENABLED=true`). Пока `SMTP_HOST` не задан, код
подтверждения не отправляется письмом, а пишется в журнал сервера:

```bash
docker compose logs backend | findstr "код для входа"
```

Для промышленной эксплуатации заполните параметры `SMTP_*` в `.env`.

## Что демонстрирует MVP

1. **Приём** — загрузка PDF/скана → ClamAV → WORM-хранение → OCR → индексация.
   Статус документа обновляется в интерфейсе в реальном времени.
2. **AI-поиск** — три режима: гибридный (смысл + слова), семантический (по смыслу),
   ключевой. Ищет по распознанному тексту, а не только по названию.
2а. **ИИ-агент (диалог)** — диалоговое окно с памятью: задаёте вопросы по
   СОДЕРЖИМОМУ документов, включая уточняющие («а на какой срок он заключён?»).
   Агент ищет по архиву, читает документы и формирует ответ со ссылками на
   источники; показывает свои действия. Всё локально (Ollama), данные не
   покидают периметр. Первый запуск скачивает модель (~2 ГБ).

   Режимы (`.env` → `AGENT_TOOL_LOOP`): по умолчанию `false` — надёжный
   retrieval-ответ (подходит для `qwen2.5:3b` на CPU). Для автономного
   tool-calling агента переключите на `true` и используйте модель 7b+
   (`OLLAMA_MODEL=qwen2.5:7b`) — качественнее, но медленнее на CPU.
3. **ЭЦП РК** — в карточке документа кнопка «Подписать и проверить ЭЦП» вызывает
   NCALayer, получает CMS и проверяет его на сервере (извлечение ИИН/ФИО подписанта).
4. **Роли** — admin / archivist / viewer (JWT).

## Роли и разграничение

- **admin** — всё, включая создание пользователей и удаление записей.
- **archivist** — приём, описание, проверка ЭЦП.
- **viewer** — только просмотр и поиск.
- **auditor** — аудитор ИБ (ТС-176 разд. 14 п. 5.1): журнал аудита, учётные
  записи, сессии и отчёт о попытках НСД к ПДн, без доступа к содержимому документов.

cd backend && pip install -r requirements.txt

```

```

## Ограничения MVP (дорожная карта)

- **ЭЦП ГОСТ**: НУЦ РК выпускает и ГОСТ 34.10 сертификаты. Встроенная проверка
  (`SIGNATURE_VERIFIER=local`) их не проверяет — такие подписи помечаются
  `unsupported` (личность подписанта всё равно извлекается), а RSA проверяется
  без цепочки и отзыва. Для промышленного контура — `SIGNATURE_VERIFIER=ncanode`:
  проверка по Правилам № 1187 через NCANode (ГОСТ 34.10-2015, цепочка до корня
  НУЦ РК, отзыв по OCSP); сервис включён в `docker-compose.kazpost.yml`.
- **Keycloak** — на MVP используется встроенный JWT; замена на Keycloak/OIDC — следующий шаг.
- **Ключи доступа WebAuthn** — `webauthn==2.2.0` закреплён под `cryptography` 42
  (её использует и `python-jose`); при обновлении `cryptography` до 44+ перейти
  на актуальную ветку py_webauthn.
- **Alfresco** — сознательно заменён лёгким FastAPI-ядром для скорости MVP.
